# epic-fab — API Surface Research

> Generated by Research subagent on 2026-05-21. Verified against Legendary (derrod/legendary), AchetaGames/egs-api-rs (active Fab integration), MixV2/EpicResearch, LeleDerGrasshalmi/FortniteEndpointsDocumentation, Jaren8r/EpicClients, and community gists. **Read the "Open uncertainties" section before writing code** — there is one critical finding (the launcher client does NOT support device_code) that changes the auth architecture.

---

## CRITICAL FINDING — Read This First

The task brief assumed an **OAuth 2.0 device-code grant** (RFC 8628 style: poll a token endpoint after the user enters a code at a verification URL). **That flow is not available for the Epic launcher client.** Per Jaren8r/EpicClients's permissions table:

- **`launcherAppClient2`** (`34a02cf8f4414e29b15921876da36f9a` — the one Legendary uses, and the one with Fab/library scopes) supports only: `authorization_code`, `client_credentials`, `exchange_code`, `refresh_token`. **No `device_code`.**
- **`fortnitePCGameClient`** (`ec684b8c687f479fadea3cb2ad83f5c6`) DOES support `device_code` — but it's a Fortnite client and is not known to carry Fab/launcher catalog scopes. Using it for Fab is `[UNCERTAIN — likely won't authorize Fab endpoints]`.

**What Legendary actually does on Linux** (verified in `legendary/api/egs.py` and `legendary/core.py`):

1. Open `https://www.epicgames.com/id/api/redirect?clientId=34a02cf8f4414e29b15921876da36f9a&responseType=code` in the user's default browser.
2. User logs in (handles MFA in the browser, transparent to the CLI).
3. Epic redirects to a JSON page containing `{"authorizationCode": "<32-char hex>"}`.
4. User pastes the code into the CLI.
5. CLI POSTs `grant_type=authorization_code&code=<code>&token_type=eg1` to the token endpoint with HTTP Basic auth.

This is **not** a true device-code flow — it's an authorization-code grant with a manual paste step. It works headlessly on Linux because the browser runs outside the CLI process. Heroic Games Launcher and Epic-Asset-Manager use the same pattern.

**Recommendation:** Implement the authorization-code-with-paste flow. Label it "browser-link login" in the UX, not "device code." If a true `oauth/deviceAuthorization` flow is essential, document it as a future spike and accept it may require a Fortnite client that doesn't have Fab scope.

The rest of this document covers the authorization-code flow (what will actually ship) and the genuine `oauth/deviceAuthorization` flow (documented separately for completeness, marked `[UNCERTAIN for Fab use]`).

## 1. Epic OAuth 2.0 — Authorization-Code Flow (RECOMMENDED, what Legendary uses)

### 1.1 Auth host and client credentials

| Item | Value |
|---|---|
| OAuth host | `account-public-service-prod03.ol.epicgames.com` |
| Token endpoint | `https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/token` |
| Verify endpoint | `https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/verify` |
| Kill-session endpoint | `https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/sessions/kill/{accessToken}` |
| Client ID | `34a02cf8f4414e29b15921876da36f9a` (`launcherAppClient2`) |
| Client secret | `daafbccc737745039dffe53d94fc76cf` |
| Token type | `eg1` (always pass this in request bodies) |

**These credentials are public.** They are reverse-engineered from the Windows Epic Games Launcher and ship in Legendary, egs-api-rs, Heroic, and Epic-Asset-Manager. Epic has not rotated them since at least 2019. They're not a secret — they're a public-client identifier.

### 1.2 Step 1 — Browser-link URL (user opens this)

```
https://www.epicgames.com/id/api/redirect?clientId=34a02cf8f4414e29b15921876da36f9a&responseType=code
```

- User logs in (MFA handled inside the browser; CLI never sees it).
- Page redirects to a JSON document of shape `{"authorizationCode": "<32-char hex string>", "exchangeCode": null, "sid": null, "ssoV2Enabled": true}`.
- User copies the `authorizationCode` value and pastes into the CLI.

The auth code is **single-use, ~5-minute TTL**. If the user takes too long, they redo the browser step.

### 1.3 Step 2 — Token exchange (`grant_type=authorization_code`)

```
POST https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/token

Headers:
  Authorization: Basic <base64("34a02cf8f4414e29b15921876da36f9a:daafbccc737745039dffe53d94fc76cf")>
  Content-Type: application/x-www-form-urlencoded
  User-Agent: UELauncher/11.0.1-14907503+++Portal+Release-Live Windows/10.0.19041.1.256.64bit

Body (form-urlencoded):
  grant_type=authorization_code
  code=<the 32-char code the user pasted>
  token_type=eg1
```

**Pre-computed Basic header value** (paste-safe, validated against Legendary's runtime construction):
`Basic MzRhMDJjZjhmNDQxNGUyOWIxNTkyMTg3NmRhMzZmOWE6ZGFhZmJjY2M3Mzc3NDUwMzlkZmZlNTNkOTRmYzc2Y2Y=`

### 1.4 Token response shape

Verified field set (from FortniteEndpointsDocumentation/Token.md, observed in egs-api-rs's `UserData` struct, and Legendary's `start_session()` return):

```jsonc
{
  "access_token": "eg1~eyJ...",              // JWT-ish, ~1500 chars, prefix "eg1~"
  "expires_in": 28800,                        // seconds — typically 8h
  "expires_at": "2026-05-21T20:00:00.000Z",  // ISO 8601 UTC
  "token_type": "bearer",
  "refresh_token": "eg1~eyJ...",              // also prefixed eg1~
  "refresh_expires": 86400,                   // seconds — typically 24h, sometimes 30 days
  "refresh_expires_at": "2026-05-22T20:00:00.000Z",
  "account_id": "abc123def456...",            // 32-char hex
  "client_id": "34a02cf8f4414e29b15921876da36f9a",
  "internal_client": true,
  "client_service": "launcher",
  "displayName": "GeraldStarks",
  "app": "launcher",
  "in_app_id": "abc123def456...",             // = account_id
  "product_id": "prod-fn",
  "application_id": "fghi"                    // varies
}
```

`scope` field: `[UNCERTAIN]` — not consistently observed in the launcher-client response. Treat absence as normal.

### 1.5 Refresh flow (`grant_type=refresh_token`)

Exact request body Legendary uses (verbatim from `start_session()`):

```
POST https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/token

Headers: (same as token exchange — Basic + UA + form content-type)

Body:
  grant_type=refresh_token
  refresh_token=<refresh_token from prior response>
  token_type=eg1
```

Response shape is identical to 1.4 — a fresh `access_token` + `refresh_token` pair. Always store the new refresh token; refresh tokens may or may not rotate but Epic sometimes invalidates the old one.

**Refresh-when:** Legendary refreshes if the access token has under 10 minutes remaining (`abs(td.total_seconds()) > 600`). Mirror that threshold.

### 1.6 What happens with MFA

MFA is handled entirely in the browser step (1.2). By the time the user pastes the `authorizationCode` into the CLI, MFA has already been satisfied. The CLI never sees TOTP codes, SMS codes, recovery codes, or email verification. This is the main reason this flow is preferable to a username/password grant — and the reason the legacy `password` grant is no longer worth trying.

## 2. Epic OAuth — True device-code flow (`oauth/deviceAuthorization`)

> Documented for completeness. `[UNCERTAIN]` whether this can be used with a client that has Fab scope. Implementer: do not pick this path unless 1.2's browser-link UX is unacceptable AND testing confirms `fortnitePCGameClient` can hit Fab endpoints.

### 2.1 Init request

```
POST https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/deviceAuthorization

Headers:
  Authorization: Basic <base64(clientId:clientSecret)>      # client MUST be one with device_code scope
  Content-Type: application/x-www-form-urlencoded

Body:
  prompt=login
```

**Important precondition** per MixV2/EpicResearch: you must already hold a `client_credentials` access token from the same client before calling `deviceAuthorization`. So the call sequence is:

1. POST `/oauth/token` with `grant_type=client_credentials` (no body fields beyond grant_type) → get app-level access token.
2. POST `/oauth/deviceAuthorization` with `Authorization: Bearer <that token>` (NOT Basic) and body `prompt=login`.

`[UNCERTAIN]` — whether the auth header on step 2 is Basic-with-client-creds or Bearer-with-app-token. Both patterns appear in different community writeups. The MixV2 doc implies Bearer; egs-api-rs has no implementation to cross-check.

### 2.2 Init response (RFC 8628 shape)

`[UNCERTAIN — field names not documented in any source I could verify]`. RFC 8628 standard shape, which Epic appears to follow loosely:

```jsonc
{
  "device_code": "<long opaque string>",
  "user_code": "ABCD-EFGH",                    // short human-readable
  "verification_uri": "https://www.epicgames.com/activate",        // [UNCERTAIN — see 2.4]
  "verification_uri_complete": "https://www.epicgames.com/activate?userCode=ABCD-EFGH",
  "expires_in": 600,
  "interval": 5,
  "client_id": "<the client id>"
}
```

### 2.3 Token exchange (`grant_type=device_code`)

```
POST https://account-public-service-prod03.ol.epicgames.com/account/api/oauth/token

Headers:
  Authorization: Basic <base64(clientId:clientSecret)>
  Content-Type: application/x-www-form-urlencoded

Body:
  grant_type=device_code
  device_code=<from init response>
```

Poll at `interval` seconds. RFC 8628 status codes (`authorization_pending`, `slow_down`, `access_denied`, `expired_token`) — `[UNCERTAIN]` whether Epic returns these exact strings.

### 2.4 Verification URL the user visits

`[UNCERTAIN]` — `https://www.epicgames.com/activate` is the public-facing device-activation page for console linking (Fortnite on Xbox/PlayStation/Switch). It is **not confirmed** that the Account Service's `oauth/deviceAuthorization` user-code maps to that same page. The MixV2 docs say "open the `verification_uri_complete` URL" but don't quote the host returned. Worth a one-shot test before committing.

## 3. Fab REST API

Source of truth: AchetaGames/egs-api-rs `src/api/fab.rs`. This is the only complete, working, recent implementation I located. Every URL below is a verbatim string literal from that file (templating shown as `{}`).

### 3.1 Base URL + auth header

| Item | Value |
|---|---|
| Host (primary) | `https://www.fab.com` |
| URL families | `/i/...` (interactive — CSRF + cookie), `/e/...` (external — Bearer), `/p/...` (programmatic — Bearer) |
| Auth header | `Authorization: Bearer <access_token>` (the Epic access_token from §1.4 — no separate Fab token exchange) |

The `/e/` and `/p/` URL families accept the Epic bearer directly. The `/i/` family is the browser-internal API and prefers cookie + `x-csrftoken` from the `fab_csrftoken` cookie. For a Linux CLI, **use `/e/` and `/p/` endpoints exclusively** — Bearer-only, no cookie jar needed.

`[UNCERTAIN]` — whether Fab requires any extra header beyond `Authorization` and `Accept: application/json`. egs-api-rs does not add Epic-specific headers (no `X-Epic-Device-ID`, no special UA). Recommend setting `User-Agent: epic-fab/0.1 (linux)` to be a polite citizen but no evidence it's required.

### 3.2 Library listing — owned assets

```
GET https://www.fab.com/e/accounts/{account_id}/ue/library?count=100
GET https://www.fab.com/e/accounts/{account_id}/ue/library?cursor={cursor}&count=100
```

- `{account_id}` is the `account_id` from the token response (§1.4), 32-char hex.
- `count` default 100; max not documented `[UNCERTAIN]`.
- Pagination via cursor — first page omits `cursor`, subsequent pages pass `cursors.next` from prior response.

**Response shape** (from egs-api-rs `FabLibrary` deserialization):

```jsonc
{
  "cursors": {
    "next": "<opaque cursor string, or null on last page>"
  },
  "results": [
    {
      // FabLibraryItem — exact field names [UNCERTAIN], egs-api-rs hides the struct
      // Observed/inferred fields from community reverse-engineering:
      "asset_id": "...",       // [UNCERTAIN — may be "uid" or "artifact_id" or "assetId"]
      "title": "...",
      "description": "...",
      "namespace": "...",      // required for asset_manifest call
      "artifact_id": "...",    // required for asset_manifest call
      "added_at": "...",       // ISO 8601
      "category": "...",
      "thumbnail_url": "...",
      "distribution_method": "ASSET_PACK" | "PROJECT" | "PLUGIN" | ...,
      // ...
    }
  ]
}
```

**Action for implementer:** make the first `library?count=100` call against a real account in a spike, dump the JSON, and fill in the struct definition before coding. The egs-api-rs source has the Rust struct but only via Cargo doc generation; the field-rename serde attrs aren't visible from the README.

### 3.3 Asset detail / listing info

```
GET https://www.fab.com/i/listings/{listing_uid}
```

Returns full listing info including offers, licenses, pricing, screenshots, seller info, UE engine compat. `{listing_uid}` is a UUID-format string (e.g. `c8f408b5-ae61-4465-bb6f-a51f587b809b`). It is **not** the same as `account_id` or `artifact_id`.

`[UNCERTAIN]` — relationship between `library` result's `asset_id`/`artifact_id` and `listings`'s `uid`. egs-api-rs has both `fab_library_items()` and `fab_listing(uid)` but the docs don't show the bridge. Likely there is a `listing_uid` field on each library item.

Related endpoints (verbatim from `fab.rs`):

```
GET https://www.fab.com/i/listings/{uid}/asset-formats/unreal-engine        # UE version compat
GET https://www.fab.com/i/users/me/listings-states/{uid}                    # ownership/wishlist state
GET https://www.fab.com/i/listings/search?{params}                           # search/browse
```

Search query params (from `fab.rs`): `q`, `channels`, `listing_types`, `categories`, `sort_by`, `count`, `cursor`, `aggregate_on`, `in`, `is_discounted`, `is_free`, `min_discount_percentage`, `seller`.

### 3.4 Download manifest — the two-step download

Fab uses a **two-step manifest pattern** identical to Epic Games Store's binary-pack format:

#### Step 1 — Get signed distribution points

```
POST https://www.fab.com/e/artifacts/{artifact_id}/manifest

Headers:
  Authorization: Bearer <access_token>
  Content-Type: application/json

Body:
  {
    "item_id": "<asset_id from library>",
    "namespace": "<namespace from library>",
    "platform": "Windows"
  }
```

`platform` accepts `Windows` (default in egs-api-rs), `[UNCERTAIN]` whether `Linux`, `Mac` are valid — for raw asset packs (Quixel-style FBX/textures) platform is mostly cosmetic. For UE plugins with platform-specific binaries it matters.

**Response shape** (verified):

```jsonc
{
  "download_info": [
    {
      "manifest_url": "https://<signed-cdn-host>/.../manifest.bin?Expires=...&Signature=...",
      "distribution_point_base_url": "https://<cdn-host>/...",
      // additional fields [UNCERTAIN]
      // egs-api-rs's DownloadInfo carries fields used to reconstruct chunk URLs
    }
    // multiple entries — multi-CDN distribution
  ]
}
```

CDN hosts observed in the wild (community-reported, not all from one source): `cloudflare.epicgamescdn.com`, `epicgames-download1.akamaized.net`, `download.epicgames.com`, `fastly-download.epicgames.com`. Pick the first that responds 200 to a HEAD.

#### Step 2 — Fetch the binary manifest

```
GET <manifest_url from step 1>
```

The response body is Epic's **binary manifest format** (little-endian, optionally zlib-compressed, with magic number header, SHA hash, chunk list, file list). Parsing this format is non-trivial — see VastBlast/EpicManifestDownloader (Node.js reference) or meszmate/manifest (Go reference). Epic also serves a JSON manifest variant for some assets; egs-api-rs parses both.

`[UNCERTAIN]` — whether Fab assets ever ship as a single zip rather than a chunked binary manifest. Quixel Megascans assets that migrated to Fab are reported to come as chunked manifests; some plugins may be simple direct downloads. Test before assuming.

#### Step 3 — Per-file download info (alternate path)

```
GET https://www.fab.com/p/egl/listings/{listing_uid}/asset-formats/{format_id}/files/{file_id}/download-info
```

Returns a direct signed CDN URL for one specific file. Used by `fab_file_download_info()` in egs-api-rs. Useful for sparse "just this one FBX" workflows where you don't want to parse the full manifest. `[UNCERTAIN]` — exact response shape; egs-api-rs has a `FabFileDownloadInfo` struct but field names aren't visible from outside.

### 3.5 Auth header summary table

| Endpoint | Auth |
|---|---|
| `GET /e/accounts/{account_id}/ue/library` | `Authorization: Bearer <epic_access_token>` |
| `POST /e/artifacts/{artifact_id}/manifest` | `Authorization: Bearer <epic_access_token>` |
| `GET /i/listings/{uid}` | `Authorization: Bearer <epic_access_token>` (works) OR cookie+CSRF (browser native) |
| `GET /p/egl/.../download-info` | `Authorization: Bearer <epic_access_token>` |
| Signed CDN URL (from manifest) | NO auth header — the signature in the URL is the auth |

**No separate Fab-specific token exchange.** The Epic bearer is the Fab bearer.

## 4. Known gotchas

### 4.1 Rate limits

- `[UNCERTAIN]` — no published rate limit. Community reports:
  - Fab search endpoint will start returning 429 after ~10 rapid sequential calls. Throttle to ~1 req/sec on search.
  - Library listing tolerates fast paginated reads (the cursor flow is intended for clients walking the whole library).
  - Manifest endpoint — no reports of throttling, but each call returns a fresh signed URL set with ~hours TTL, so cache and don't refetch.
- Signed CDN URLs typically expire in 4–24 hours `[UNCERTAIN — varies by CDN]`. Plan for re-requesting the manifest if a long-running download is interrupted.

### 4.2 Header requirements

- **User-Agent matters.** Default `curl/X.Y.Z` and default `reqwest/X.Y` get 403 on some Epic endpoints, especially under Cloudflare. Use Legendary's UA verbatim for the Epic Account Service:
  `UELauncher/11.0.1-14907503+++Portal+Release-Live Windows/10.0.19041.1.256.64bit`
  For Fab specifically, egs-api-rs does NOT override UA — reqwest's default works. Recommend testing without an override first; only add a UA if you see 403s.
- **`X-Epic-Device-ID`** — listed in FortniteEndpointsDocumentation as required for `/oauth/token` but Legendary and egs-api-rs both omit it and work fine. Treat as optional. If you want to be safe, generate a stable random 32-char hex on first run and pass it on every token call.
- **TLS:** Standard TLS 1.2+. No client cert. No SNI quirks.

### 4.3 Recent API changes (late 2025 / early 2026)

- Fab launched late 2024 consolidating Quixel Bridge + Sketchfab marketplace + UE Marketplace. Quixel Bridge is being deprecated; the Bridge UE plugin still works but routes through Fab APIs underneath.
- `/i/users/me/acquired-content?listing_ids=` (older endpoint) now returns 400 — superseded by `/i/users/me/listings-states/{uid}`. Don't use the old endpoint.
- `/e/accounts/{account_id}/ue/library` is the **current** library endpoint as of egs-api-rs's last update. The `?cursor=` pagination is post-launch (cursor pagination replaced earlier offset-based pagination).
- **Sketchfab download API** at `support.fab.com/s/article/API-Overview` is documented as "API documentation available" but it's the legacy Sketchfab REST API, not the Fab unified surface. Don't conflate them — that API requires Sketchfab API tokens, not Epic OAuth.
- **No official public Fab API.** Epic forum threads from 2024–2025 confirm Epic has not committed to publishing one. Everything in §3 is community-reverse-engineered.

### 4.4 MFA interaction

- With the **authorization-code-via-browser** flow (§1, recommended): MFA is fully transparent — handled in the browser before the auth code is issued. The CLI never sees MFA artifacts.
- With the **device-code** flow (§2, not recommended): MFA `[UNCERTAIN]` — RFC 8628 expects the browser side to handle MFA same as a normal login, but Epic's implementation isn't documented.
- The legacy username+password grant (`grant_type=password`) **does NOT bypass MFA** and is no longer supported by Epic for accounts with MFA enabled (effectively all accounts post-2022). Do not implement this flow.

### 4.5 Refresh token rotation

- Refresh tokens **may** rotate on use. Legendary always overwrites stored credentials with the latest response. Do the same — never reuse a refresh token after a successful refresh.
- Long idle (>refresh_expires) means the user must re-do the browser-link step. There is no way around this without persistent device-auth credentials (see §2's `device_auth` grant, distinct from `device_code`, which IS a long-lived persistent credential — but creating it requires already-authenticated session).

### 4.6 Token type prefix

All Epic access/refresh tokens are JWT-shaped strings **prefixed with `eg1~`** (e.g. `eg1~eyJhbGciOi...`). The `token_type=eg1` form field in requests refers to this prefix. Don't strip the prefix when storing or passing to Fab — it's part of the token.

## 5. Open uncertainties (the implementer MUST verify before relying on these)

These are the items marked `[UNCERTAIN]` above, collected for a single verification spike:

1. **Exact field names on `FabLibrary.results[]` items** — run `GET /e/accounts/{id}/ue/library?count=1` against a real account, dump the JSON, lock the struct.
2. **The bridge field between library items and listings UIDs** — does a library item carry `listing_uid` directly? Or does `artifact_id` map 1:1 to a listing? Test by cross-referencing one library item to `/i/listings/{uid}`.
3. **Exact request and response shape of `oauth/deviceAuthorization`** if you choose that path — community docs are incomplete. The verification URL host (`epicgames.com/activate` vs something else) is also unverified.
4. **Whether `fortnitePCGameClient` can hit Fab endpoints** — only matters if device_code is chosen. Test with a `client_credentials` token from that client against `GET /e/accounts/{id}/ue/library` — expect 401/403 if scope-blocked.
5. **`X-Epic-Device-ID` header** — required or optional? Test by omitting on first run and watching for 400s.
6. **`platform` field values** for `POST /e/artifacts/{id}/manifest` — `Windows` works; `Linux`, `Mac`, `IOS`, `Android` `[UNCERTAIN]`.
7. **Signed CDN URL TTL** — varies by CDN; check `Expires=` query param on the first manifest call to confirm.
8. **Search rate limit** — exact threshold `[UNCERTAIN]`. Build in exponential backoff on 429.
9. **`FabFileDownloadInfo` response shape** — only available by reading egs-api-rs source or running one call.
10. **Whether single-file `download-info` works for all assets or only some formats** — UE plugins vs Megascans vs Sketchfab models may differ.

These can all be resolved in a single ~30-minute spike against a real Fab library with one owned asset and one bought asset.

## Appendix — Suggested implementation shape

For the implementer, the auth module roughly looks like:

```
auth.ts:
  - openBrowserLinkUrl() → opens https://www.epicgames.com/id/api/redirect?clientId=...&responseType=code
  - promptForAuthCode() → readline, 32-char hex
  - exchangeAuthCode(code) → POST oauth/token grant_type=authorization_code → returns Session
  - refreshSession(session) → POST oauth/token grant_type=refresh_token → returns Session
  - persistSession(session) → write to ~/.config/epic-fab/session.json (0600)
  - loadSession() → read + auto-refresh if <10min remaining

api.ts:
  - fab.listLibrary({cursor?, count=100}) → GET /e/accounts/{account_id}/ue/library
  - fab.getListing(uid) → GET /i/listings/{uid}
  - fab.getManifestPointers(artifactId, {itemId, namespace, platform='Windows'}) → POST /e/artifacts/{id}/manifest
  - fab.fetchSignedManifest(manifestUrl) → GET (no auth, signed URL)
  - fab.getFileDownloadInfo(listingUid, formatId, fileId) → GET /p/egl/...

download.ts:
  - parseEpicBinaryManifest(buf) → {files, chunks}
  - downloadChunks(...) → parallel, resumable
  - reassembleFiles(...) → writes to ~/.local/share/epic-fab/{listing_uid}/
```

The session storage shape mirrors egs-api-rs's `UserData`: store the entire token response JSON, refresh in place, never lose `account_id`.
